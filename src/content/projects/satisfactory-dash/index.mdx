## The problem

Satisfactory players who run a dedicated server can't see how their factory is doing without joining the game. satisfactory-dash is a dashboard for that: production, overflow and power, live. It runs in production at [satis-manager.com](https://satis-manager.com), and a [public demo](https://demo.satis-manager.com) shows it without a game server.

For its first months the backend and its database ran on my gaming PC, beside the game itself. That PC was already short of memory and was never meant to be a server. This is the story of moving the service off it, without losing data and without a way in to my home network.

In Satisfactory, each machine runs one recipe. Ingredients arrive on a belt and wait in its input slots, the machine crafts them, and the result sits in its output slot until the outgoing belt takes it away. For every machine, the dashboard reads how stocked those input slots are, whether the output slot is full, and how fast the machine is producing compared with the rate it's set to run at.

From those readings it sorts every machine into one of six states, and the order of its checks decides which one. A machine that's starved of ingredients is underfed; one whose output has nowhere to go is backed up. Try it:

## Finding the bottleneck

Knowing a machine is underfed doesn't say why. The cause can be several machines away: a mining node that's too slow, a belt of the wrong tier, a splitter sending half the flow elsewhere, or a missing input. The Factory page's Bottlenecks section walks from each underfed or backed-up machine to the root cause and lists the top ten, each with the belt that caps it ([ADR-0048](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0048-bottleneck-finder.md)).

It works in two levels. First it follows items through the factory: which machines make what a starved machine needs, and how much they actually produce. Then it treats every belt, lift and pipe as a pipe of fixed capacity and runs a max-flow (Dinic's algorithm) over the whole network. The smallest cut in that network is the conveyor that limits the flow, and the page names it with its tier, rate and position ([#570](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/570), [#575](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/575), [#578](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/578), [#581](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/581)).

The finder is a pure function of the factory and its connections, so it is easy to test: it has 48 tests, and on a generated factory ten times the size of mine it ran in about 50 ms. Before building the visible part I checked two things on a separate test server, never my own game: that a rebuilt belt shows up on the next read, and what unit a pipe's speed is reported in. Both held, and the second changed the design: a belt or pipe reports its tier's maximum, not the flow actually moving, so the finder can name a capacity cap but cannot see how full a belt is.

## The production planner

The bottleneck finder explains one starved machine. The Planner answers a wider question: what does the whole factory look like, and what feeds what? It draws the factory as a graph, and the hard part is deciding what not to draw. The largest site on my save has 385 machines, joined by a great many belt segments ([ADR-0050](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0050-production-planner.md)).

The first step collapses the belt segments into a graph of machine groups and the links between them. On that site that is 385 machines in 160 groups with 204 links. Loops, where a belt feeds back into its own line, are found as strongly connected components (Tarjan's algorithm).

Then comes the question of what counts as one factory. The first rule was distance: machines within 150 m of each other were one site. I measured the result read-only on my own save, and it was wrong in a useful way. That one "site" was 10 separate weakly connected components that the proximity rule had glued together, 91 of its 204 links were bridges (cut one and the graph falls in two), and the graph was 8 layers deep. A better rule had to follow the items, not the map.

That is the logical factory ([ADR-0055](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0055-planner-logical-factories.md), [#669](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/669)). Each group is assigned by its share of output to each final product, worked out from the machines' maximum rates, so there is no live belt polling. A remote raw-material farm joins the factory it feeds, not the one it stands near. Try it, on a made-up example:

<FactoriesFigure />

A group that sends less than 95% of its output to one product is marked shared, rather than forced into a factory it only half belongs to. Small dependent offshoots fold into their factory: fewer than 4 machines, every input from one factory, and nothing leaving by transport, depot or the sink. Collapsing a whole upstream subtree on the canvas uses post-dominators (the Cooper–Harvey–Kennedy algorithm). The reduction is cheap: about 1.5 ms on a real-size graph, and about 98 ms in the capped worst case.

## How data gets in

The game only answers on the PC itself, so a small agent runs there. It reads the game and pushes what it sees out to the backend, one <span class="tok tok-snapshot"><i>●</i>snapshot</span> at a time, oldest first. The cloud never connects in to the PC, and the game's credentials never leave it ([ADR-0031](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0031-edge-agent.md)).

Anything the agent can't deliver yet waits in its <span class="tok">queue</span>. If something along the way is down, an <span class="tok tok-error"><i>●</i>error</span> comes back; the agent keeps that snapshot and tries again later, waiting a little longer each time, with some randomness so that many agents don't all retry at once ([pusher.ts](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/agent/src/pusher.ts), [backoff.ts](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/agent/src/backoff.ts)).

<OutageFigure />

When the link breaks, something has to give. The system picks availability: the dashboard keeps answering with the last snapshot it has, [marked stale](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/frontend/src/components/DataAge.tsx), rather than going blank, and the agent keeps collecting. The cost is consistency: history arrives late, and if the outage outlasts the queue (about ten minutes of snapshots, [agentRunner.ts](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/agent/src/agentRunner.ts)), the oldest readings are <span class="tok tok-dropped"><i>○</i>dropped</span> for good ([queue.ts](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/agent/src/queue.ts)). For a live dashboard, the newest data matters most.

The figure's database toggle shows one more split: with the database down, the backend stays up and says so, and nothing restarts it. AWS only checks that the backend's process is alive; an outside monitor watches the database ([#425](https://github.com/Sour-Dev-Home/satisfactory-dash/issues/425)).

## The move to AWS

AWS's Free plan came with credits, so the backend moved to ECS Fargate (one small ARM task, with Cloudflare's tunnel beside it) and the database to RDS PostgreSQL ([ADR-0034](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0034-backend-on-aws.md)). The estimate was about $33 a month; a budget alarm fires at $40 ([variables.tf](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/infra/aws/variables.tf)). Two rules shaped it: nothing in the app may depend on AWS, so leaving is as boring as arriving, and backups leave AWS entirely, to Backblaze B2 with a key that can write but not delete ([ADR-0035](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0035-backups-off-aws.md)).

Moving a live service is mostly about never being stuck. The [runbook](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/runbooks/aws.md) breaks the move into five steps, and no step starts until the one before it checks out. Each has a rollback, and until the last one, the PC still has every byte. The <span class="tok tok-backup"><i>■</i>final backup</span> is the bridge: taken after writes stop, restored into RDS, and checked table by table before anything points at AWS. Only then does the <span class="tok tok-route"><i>━</i>route</span> for `api.satis-manager.com` move.

## Keeping it running

A service you can't watch needs to say when it is failing. Background workers now count consecutive failures and, past a threshold of about five minutes of failing, log one error that a CloudWatch alarm picks up. An alert evaluator heartbeat shows it is still ticking, and an unhandled error logs a sanitised line and exits instead of limping on ([#565](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/565)). The alarms are defined in Terraform and live on AWS, with a second one for bursts of failed sign-ins.

I also ran an OWASP Top 10:2025 check with three read-only security reviews, `npm audit` and a personal-data scan. It found no High findings. It did find a Medium, the backend's base image pinned by tag instead of by digest, and the fixes include pinning it and a one-year HSTS header ([#563](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/563), [#566](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/566)).

Users can now delete their account, or leave a server, from Settings. The server asks for a recent sign-in first, and takes its locks in a fixed order so a deletion racing a transfer of ownership waits instead of removing a server from its new owner. Privacy and terms pages describe it ([#556](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/556), [#564](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/564), [#569](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/569)).

The map shows the game's own resource icons and can filter by resource type, in use or free, and building state, remembered per browser ([#576](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/576), [#582](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/582)).

There is also an operator-only metrics page, out of the nav and reached from the command bar. It shows latency percentiles as bucket upper bounds ("p95 ≤ 200 ms"), refused and dropped counters, and alert quality by month: how many fired, how many flapped (fired then cleared within five minutes, a stand-in for false alarms) and the median time to clear ([ADR-0036](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0036-metrics-page.md), [#665](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/665), [#667](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/667)). The demo site shows it with labelled sample data.

## Shipping it

Deploys used to be a manual step, and I got tired of doing them by hand. Now a merge that changes the backend images builds them, then deploys the same digests to staging and, if staging passes, to production. A merge that touches no backend code skips green ([ADR-0049](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0049-automated-staged-deploys.md), [#585](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/585), [#598](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/598), [#599](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/599), [#601](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/601), [#602](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/602), [#604](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/604), [#605](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/605)). Several runs on 2026-10-25 went resolve, staging, production, all green.

- **No stored cloud keys.** GitHub Actions assumes least-privilege AWS IAM roles through OIDC. The trust policy pins one workflow file on `main`, one GitHub environment, and GitHub's immutable subject (the owner and repository ids).
- **Throwaway staging.** A one-shot ECS Fargate task with its own PostgreSQL, cluster, egress-only network, secrets and tunnel behind Cloudflare Access. It migrates the schema production has now, then this release's migrations, then signs in and checks the API, and is always torn down. It costs nothing when idle and well under a cent per run.
- **Safe production rollout.** Migrations run first and are expand-only, which a CI contract check enforces. Then the ECS rollout, then a 10-minute watch on the error alarms with automatic rollback, plus an ECS alarm and circuit-breaker rollback, a health check and a release record in SSM. Rollback and redeploy are each one click.
- **Configuration vs. image.** Terraform owns the configuration and CI owns which image runs. The deploy scripts have 63 unit tests against a fake AWS, the Terraform has 58 mock-provider tests, and each PR had a security review.

Since then, a few more pieces ([ADR-0054](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0054-deploy-uptime.md), [#643](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/643), [#647](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/647), [#652](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/652), [#653](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/653)). Backend build inputs that haven't changed skip the deploy, found by an inputs-hash label on the image. A Postgres advisory lock elects a leader (5 seconds; failover takes about 4.5), so only one task runs the background work. And the dashboard shows a calm "updating" notice during a deploy gap.

Zero-downtime rolling deploys are not built.

## Could the agent move into the game?

The backend left the PC, but the agent can't: it has to sit beside the game. Most players rent their server from a host and have no machine to run it on. So the idea is to make the agent a server mod, written against Satisfactory's mod loader, SML ([ADR-0039](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0039-mod-as-end-state-research.md)).

Modding is thinly documented, and an AI assistant will happily invent an engine call that doesn't exist. So nothing gets built on trust. The work passes evidence gates, and no product code is written until a later decision record approves it. Every engine or SML call in the [mod repository](https://github.com/Sour-Dev-Home/satisfactory-dash-mod) needs a row citing the header file and line that declares it, and CI fails any call without one.

<Sidenote id="refused" lead="true story">The harness refused its very first run: my own game server was still up.</Sidenote>

The questions are answered by small throwaway mods, each run by a harness against a separate test server, which produces a pass or a fail plus the logs behind it. So far, a mod loads on the dedicated server ([#6](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/6)) and can send an HTTP request ([#7](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/7)). HTTPS works too, and a server with the wrong certificate is refused ([#8](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/8)). And a mod posting every 30 seconds leaves the server's tick rate where it was: 22.0 against 22.3 without it ([#9](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/9)). The first run of that test failed: the server runs faster for a while after it boots, and the harness had been measuring across the drop.

The second round answered the rest:
- A mod reads a credential from its config without ever logging it ([#14](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/14)).
- It enrols with a one-time code and pushes a snapshot to a throwaway copy of the backend ([#15](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/15)).
- On a copy of my own save, it reads the power grid within 1% of what an existing monitoring mod reports ([#16](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/16)).

That last one failed first too. The game joins circuits behind a switch into one group, and the pass rule had only judged lone circuits ([#18](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/18)).

All seven claims hold on a real server, so the gates did their job. The decision record had parked the build until a player's rented server couldn't run the agent. I un-parked it with my own goal instead, moving the agent off my PC and into the mod ([ADR-0042](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0042-build-the-mod.md)). The build has started: its plan is merged ([#28](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/28)), and so is its first task, the HTTP transport and the game module, with a probe that runs on the test server ([#29](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/29)). Until the mod matches the agent, the agent stays the supported path.

## What I’d do differently

The credits run out in a few months, and the exit is already written: the same image and `compose.yaml` on a cheap VM, with the data moving by `pg_dump` and `pg_restore`, the path the restore rehearsals use. If I did it again I'd build that exit first and treat AWS as the second home, not the first.

## How it was built

<Sidenote id="agents" lead="psst">Development started with three Claude agents: a developer, an architect and a frontend agent. Midway through I tried more thorough task management with my own tool, lanes, and it ran most of the build before I retired it.</Sidenote>

I built satisfactory-dash with Claude Code, most of it through [lanes](https://github.com/Sour-Dev-Home/lanes): one fresh session per GitHub issue, gated by required checks and reviewer agents. Its gates cost more than they returned here, though: even a dependency bump needed its own issue, and I kept stepping in by hand. So I replaced it with plain CI/CD ([ADR-0043](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0043-retire-lanes.md), [#482](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/482)). A session opens the pull request, runs the reviewer agents itself (tests, UI and security), and the change merges once the required checks pass.

CI now runs only what a change touches ([#483](https://github.com/Sour-Dev-Home/satisfactory-dash/pull/483)). A one-line backend change checks in 1m47s instead of the full 4m29s, and a docs-only change in 26 seconds. The [repository](https://github.com/Sour-Dev-Home/satisfactory-dash) is public.
