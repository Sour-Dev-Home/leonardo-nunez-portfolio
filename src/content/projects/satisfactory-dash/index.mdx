## The problem

Satisfactory players who run a dedicated server can't see how their factory is doing without joining the game. satisfactory-dash is a dashboard for that: production, overflow and power, live. It runs in production at [satis-manager.com](https://satis-manager.com), and a [public demo](https://demo.satis-manager.com) shows it without a game server.

For its first months the backend and its database ran on my gaming PC, beside the game itself. That PC was already short of memory and was never meant to be a server. This is the story of moving the service off it, without losing data and without a way in to my home network.

## How data gets in

The game only answers on the PC itself, so a small agent runs there. It reads the game and pushes what it sees out to the backend, one <span class="tok tok-snapshot"><i>●</i>snapshot</span> at a time, oldest first. The cloud never connects in to the PC, and the game's credentials never leave it ([ADR-0031](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0031-edge-agent.md)).

Anything the agent can't deliver yet waits in its <span class="tok">queue</span>. If something along the way is down, an <span class="tok tok-error"><i>●</i>error</span> comes back; the agent keeps that snapshot and tries again later, waiting a little longer each time, with some randomness so that many agents don't all retry at once ([pusher.ts](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/agent/src/pusher.ts), [backoff.ts](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/agent/src/backoff.ts)).

<OutageFigure />

When the link breaks, something has to give. The system picks availability: the dashboard keeps answering with the last snapshot it has, [marked stale](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/frontend/src/components/DataAge.tsx), rather than going blank, and the agent keeps collecting. The cost is consistency: history arrives late, and if the outage outlasts the queue (about ten minutes of snapshots, [agentRunner.ts](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/agent/src/agentRunner.ts)), the oldest readings are <span class="tok tok-dropped"><i>○</i>dropped</span> for good ([queue.ts](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/agent/src/queue.ts)). For a live dashboard, the newest data matters most.

The figure's database toggle shows one more split: with the database down, the backend stays up and says so, and nothing restarts it. AWS only checks that the backend's process is alive; an outside monitor watches the database ([#425](https://github.com/Sour-Dev-Home/satisfactory-dash/issues/425)).

## The move to AWS

AWS's Free plan came with credits, so the backend moved to ECS Fargate (one small ARM task, with Cloudflare's tunnel beside it) and the database to RDS PostgreSQL ([ADR-0034](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0034-backend-on-aws.md)). The estimate was about $33 a month; a budget alarm fires at $40 ([variables.tf](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/infra/aws/variables.tf)). Two rules shaped it: nothing in the app may depend on AWS, so leaving is as boring as arriving, and backups leave AWS entirely, to Backblaze B2 with a key that can write but not delete ([ADR-0035](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0035-backups-off-aws.md)).

Moving a live service is mostly about never being stuck. The [runbook](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/runbooks/aws.md) breaks the move into five steps, and no step starts until the one before it checks out. Each has a rollback, and until the last one, the PC still has every byte. The <span class="tok tok-backup"><i>■</i>final backup</span> is the bridge: taken after writes stop, restored into RDS, and checked table by table before anything points at AWS. Only then does the <span class="tok tok-route"><i>━</i>route</span> for `api.satis-manager.com` move.

<summary>More detail: the AWS setup</summary>
<Aside>
- No load balancer, no NAT gateway and no inbound rules: the task only connects out, through the tunnel ([ADR-0034](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0034-backend-on-aws.md)).
- Secrets come from SSM Parameter Store, injected when the task starts; the app holds no AWS credentials, and no access key exists.
- One multi-architecture image runs on Fargate, on any VM, or on the PC, and a `compose.yaml` runs the whole stack on one machine, tested in CI.
- ECS checks liveness only; readiness, which includes the database, is for an external monitor ([ecs.tf](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/infra/aws/ecs.tf)).
</Aside>
</details>

## Could the agent move into the game?

The backend left the PC, but the agent can't: it has to sit beside the game. Most players rent their server from a host and have no machine to run it on. So the idea is to make the agent a server mod, written against Satisfactory's mod loader, SML ([ADR-0039](https://github.com/Sour-Dev-Home/satisfactory-dash/blob/main/docs-vault/wiki/decisions/0039-mod-as-end-state-research.md)).

Modding is thinly documented, and an AI assistant will happily invent an engine call that doesn't exist. So nothing gets built on trust. The work passes evidence gates, and no product code is written until a later decision record approves it. Every engine or SML call in the [mod repository](https://github.com/Sour-Dev-Home/satisfactory-dash-mod) needs a row citing the header file and line that declares it, and CI fails any call without one.

<Sidenote id="refused" lead="true story">The harness refused its very first run: my own game server was still up.</Sidenote>

The questions are answered by small throwaway mods, each run by a harness against a separate test server, which produces a pass or a fail plus the logs behind it. So far, a mod loads on the dedicated server ([#6](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/6)) and can send an HTTP request ([#7](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/7)). HTTPS works too, and a server with the wrong certificate is refused ([#8](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/8)). And a mod posting every 30 seconds leaves the server's tick rate where it was: 22.0 against 22.3 without it ([#9](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/9)). The first run of that test failed: the server runs faster for a while after it boots, and the harness had been measuring across the drop.

The second round answered the rest:
- A mod reads a credential from its config without ever logging it ([#14](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/14)).
- It enrols with a one-time code and pushes a snapshot to a throwaway copy of the backend ([#15](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/15)).
- On a copy of my own save, it reads the power grid within 1% of what an existing monitoring mod reports ([#16](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/16)).

That last one failed first too. The game joins circuits behind a switch into one group, and the pass rule had only judged lone circuits ([#18](https://github.com/Sour-Dev-Home/satisfactory-dash-mod/pull/18)).

All seven claims hold on a real server, so the gates did their job. The build waits, though. Its trigger in the decision record is a player whose rented server can't run the agent. And a few questions are still open, such as the game's terms on mods and the licence of a GPL mod beside this AGPL app. Until then, the agent stays the supported path.

## What I’d do differently

The credits run out in a few months, and the exit is already written: the same image and `compose.yaml` on a cheap VM, with the data moving by `pg_dump` and `pg_restore`, the path the restore rehearsals use. If I did it again I'd build that exit first and treat AWS as the second home, not the first.

## How it was built

<Sidenote id="agents" lead="psst">Development started with three Claude agents: a developer, an architect and a frontend agent. Midway through I tried more thorough task management with my own tool, lanes, and it ran the rest of the project.</Sidenote>

I built satisfactory-dash with Claude Code, most of it through [lanes](https://github.com/Sour-Dev-Home/lanes): one fresh session per GitHub issue, gated by required checks and reviewer agents, with every change reviewed by me before it merged.
